# 審査ハーネスの設計と実装状況

この文書は、Codexが書いた設計案（旧版のこのファイルとCLAUDE.md）と、AIゲームジャム運営側のClaudeが出した提案を突き合わせ、実装した内容をまとめたもの。配点・閾値・テーマは `rubric.example.json` の設定で、運営が本番前に確定する。

## 2つの提案の突き合わせ

両案は「提出物の命令に従わない」「最終決定は人間」「失敗を反対票にしない」「3基で同じ資料を見る」で一致していた。食い違った点と、採用した形は次のとおり。

| 論点 | Codex案 | 運営側Claude案 | 採用した形 |
| --- | --- | --- | --- |
| 採点項目 | 発想・遊びの設計・完成度・伝わりやすさ 各25 | テーマ20・面白さ30・体験20・完成度20・AI活用10 | 運営側の5項目と配分を基本に、Codexの「伝わりやすさ」を体験に、「発想・独創性」をテーマに統合 |
| 段階 | 0〜5、未確認は0点にしない | 1〜5、点ごとに言葉の基準 | 0〜5、全項目に0〜5点それぞれの具体例。未確認は `null` |
| 3基の重み | 項目・配点は3基で同一、人格はコメントだけ | 各人格が自分の目線の重みで採点 | **採点（0〜5）は共通の段階表**。人格別の重みは設定ファイルに明示し、ホストが計算。共通配点の合計も必ず併記 |
| 推薦 | 閾値はホストで計算、絶対推薦と相対順位を分離 | 可決・否決の演出 | 各人格の配点での合計が閾値70以上で賛成。AIは票を返さない。MAGI賞は3基の推しの多数決、割れたら推された作品の平均点（運営決定） |
| AI活用 | 製品名・推測した利用量で加減点しない | 「AIをどう使い何を工夫したか」10点 | 項目として採用。参加者の説明は主張扱いで、観測済みにはならない。製品名・量での加減点は禁止のまま |
| 入力 | 共通の観測記録、画像は全CLIの対応確認後 | 企画書・スクショ3枚・30秒動画・3行説明 | 3行説明と企画書は取り込み済み。スクショ・動画はハッシュ記録のみで**審査員には見せない**（未確認と表示）。代わりに運営が遊んだ**共通プレイ記録**を入力にする |
| 実プレイ | 未実装をできたことにしない | AIに遊ばせるのは不安定 | AIには遊ばせない。人間のプレイ記録を3基共通の証拠にする |
| ぶれ対策 | 再試行は上限と理由を記録、都合のよい再生成をしない | 3回採点して平均 | `--samples N`（1〜5）で同条件のN回を全件保存し、項目ごとに平均。1回でも失敗したら保留 |
| 注入対策 | 提出物はデータとして扱う | 見つけたら運営に知らせる | 資料ブロックの境界に毎回ランダムな印を付ける。ホストの自動検出とAIの指摘の両方を「要確認」として表示。得点には反映しない |
| 匿名化 | — | チーム名を伏せる | 審査員には作品名を見せず `作品-XXXXXX` で提示。`--redact` でチーム名等を `[非公開]` に置換 |
| 人間との組合せ | 最終は人間 | (a) 1票 + (c) 全チームに講評 | どちらにも使えるよう、`scores.csv`（人間の採点表と合わせる用）と `feedback.md`（チーム向け講評）を出力。どれにするかは運営が決める |

## 採点の流れ

1. **証拠パック**：提出ソース（F001…）、企画書・スライド・文字起こし（A001…）、3行説明（S001…）、運営のプレイ記録（P001…）に番号を振り、行番号付きで3基へ同じものを渡す。種類は「提出ソース」「参加者の主張」「運営のプレイ記録」の3つ。画像・動画（M001…）は存在とハッシュだけを記録する。
2. **各AIの出力**：項目ごとに `status`（observed / inferred / not_observed）、`score`（0〜5か `null`）、理由、限界、引用（資料ID・行番号）。講評、チーム向けの良い点・改善提案、注入の指摘、未確認事項。
3. **ホストの検証**：
   - 存在しない資料ID・行番号、逆順の行範囲、未確認なのに得点あり、得点ありで引用なし、推定で限界の説明なし、は不正出力として保留。
   - 「観測」は項目ごとに使える資料が決まっている（例：面白さ・体験・完成度はプレイ記録のみ）。条件を満たさない「観測」は推定に下げ、その旨を記録して表示する。参加者の主張だけでは観測にならない。
4. **集計（すべてホスト側）**：
   - 合計は `点数 / 5 × 配点`。未確認の項目は100点満点に換算し直さず、「確認済みの小計」と「未確認がすべて0点〜5点だった場合の範囲」を出す。
   - 各人格の票：推薦に必須の項目（面白さ・完成度）が未確認なら保留。範囲の下限が閾値以上なら賛成、上限が閾値未満なら反対、閾値をまたぐなら保留。
   - 作品の判定：賛成2票で推薦可決、反対2票で推薦否決、それ以外は保留（観測不足）。1基でも障害があれば保留（システム）。棄権と障害は分けて表示する。
   - MAGI席の得点：3基の共通配点の合計の平均。人間の審査員と並べる場合に使う。
5. **MAGI賞**（`compare` / `batch`。運営の決定、2026-10-16）：
   - 全作品を事前に3基で審査する。会場では作品ごとの審議を見せず、MAGI賞の発表だけを行う。
   - 3基がそれぞれ1作品を推す。推しはその人格の配点で最高得点の作品で、ホストが得点から決める（同点なら共通配点で比べ、それでも同点なら棄権）。
   - 2基以上が推した作品が受賞。3基一致は全会一致。
   - 3基の推しが割れた、または2票に達しない場合は、推された作品のうち3基の平均点（共通配点）が最も高い作品が受賞。同点は共同受賞。推された作品がなければ全作品から選ぶ。
   - 審議未完了の審査員がいる、または未確認項目しだいで逆転し得る作品がある場合は保留。
   - 採点は辛口（`strictness`、段階表の3点＝標準的な作品）。作品ごとの推薦の閾値は70点で、講評・記録用。
   - 審査員のプロンプトには、MAGI賞・議案・推し・順位のことを一切入れない。各審査員は1作品だけを見て採点し、推し・多数決・平均点はすべてホストが得点から計算する（テストで確認）。
   - 発表の最後に平均点の上位3作品を表示する。推しが割れた場合、推されていない作品が受賞作より高い平均点になることがあるため、画面に「MAGI賞は各AIの推しの中から決まる」と明記している。
   - 会場ではMELCHIOR等の名前ではなく、各CLIが報告した実際のモデル名（Claude・Grokは出力の `modelUsage`、Codexはログの `model:` 行）を表示する。読み取れなければ製品名。プロンプト内の人格名は変えていない。

## 版と追跡

- `protocol.json`：ハーネス版、採点設定・人格・プロンプト雛形・スキーマ雛形のハッシュ、指定モデル、試行回数。これが一致しない結果は比較を拒否する。
- `result.json`：作品の提出物ハッシュ、観測条件（プレイ記録の有無、画像を見せていないこと）、各CLIの版、各試行の結果と所要時間、ホストの補正、再利用した試行。
- プレイ記録のある作品とない作品の比較は、`--allow-mixed-observation` を付けない限り拒否する。デモと実判定、同一提出物の重複も拒否する。
- `batch` は作品ごとに `attempt-N` を作り、再実行時は完了済みを飛ばす。失敗した作品は、同じ入力・同じ設定で成功していた審査員の結果を再利用し、失敗した審査員だけを呼び直す。試行は `--max-attempts`（既定3）まで。

## 未実装・次の段階

- **画像・動画の入力**：各CLIの画像入力の方法を確認し、3基すべてに同じ画像を渡せると実機で確かめてから有効にする。それまでは見た目・動き・音は未確認として扱う。
- **再審議**：上位候補だけの2回目の審議。初回を上書きしない別ラウンドとして保存する。現状は保留にして運営判断へ渡す。
- **自動ブラウザ観測**：提出コードの実行は、CLIの認証領域やユーザーのブラウザプロファイルから分離した環境で行う。
- **CodexとGrokでの新スキーマの実疎通**：2026-10-16時点ではClaudeのみ確認済み（下記）。
